# 插件开发

**什么时候读**：新增插件、修改宿主或客户端代码、安装/重装/卸载、官方升级后功能失效。

## 包结构

**什么时候用**：新建一个插件目录时。

- `package.json`：`name` 用 `@local/<名字>`；`dsh.bundle.patch` 指向 `cordis.patch.yml`；
  有界面时加 `dsh.client`（`platform: web`、`immediately: true`、`inject` 客户端包）和 `./client` 导出
- `cordis.patch.yml`：`- insert: - id: <entryId> name: '@local/<名字>'`，需要配置时加 `config:`
- `index.js`：宿主半，导出 `apply(ctx, config)`，用 `inject` 声明依赖的服务
- `client.js`：客户端半，`window.__ModuleLoader__.load({...})` 注册 React 组件
- `locale/en.json`、`locale/zh.json`：`meta.title`、`meta.description`（插件列表显示）
- `icon.svg`

**坑**：`files` 对本地 link 安装不生效，但打包安装靠它，新增文件要记得补。

## 两半的差别

**什么时候用**：判断改完要不要重装。

- 宿主（`index.js`）：跑在 DSH 主进程，能读文件、跑 git、查会话、注册路由和投影。
  改完必须 `remove_bundle` + `install_bundle` 才生效。
- 客户端（`client.js`）：跑在浏览器，保存即热更新，刷新页面即可。

**坑**：只改 `client.js` 也去重装，会多两次审批，没必要。

## 运行环境与生效方式

**什么时候用**：改完要看效果、判断“刷新了没变”、或者排查为什么卸载了还有残留。

- 用户用的是**官方桌面客户端**（Electron，`/Applications/DeepSeek Harness.app`），页面跑在
  `dsh-app://` 这个固定 origin 下（进程参数里有 `--standard-schemes=dsh-app`），
  所以 `localStorage` 在重启、升级后都还在；`127.0.0.1:<端口>` 只是给外部浏览器访问的入口，
  端口每次启动都可能变，别拿它判断持久化。
- 客户端半改完的“刷新”= **⌘R / 菜单 View ▸ Reload / 退出重开 App**；宿主半改完要
  `remove_bundle` + `install_bundle`。
- **运行时写进 DOM 的东西不会随插件卸载撤销**：比如隐藏官方按钮时打了内联
  `style.display = 'none'`，卸载插件后旧窗口里那一行仍然是隐藏的——必须重载窗口/重开 App 才会按官方原样重渲染。
- 判断插件是否“真的在跑”：`plugin_manager` 的 `list_plugins` 看 `enabled` + `fiberPhase: active`，
  比界面现象可靠。

## 安装 / 重装 / 卸载

**什么时候用**：新增插件，或插件目录搬家之后。

1. `install_bundle`，target 传包的绝对路径
2. 它在 profile 里加一条 `link:` 记录并建软链，同时写进 `dsh.profile.bundles`
3. 搬家后必须先 `remove_bundle` 再 `install_bundle`，否则会判 `already-installed`

**坑**：每次操作都会弹审批；它不会自动升级已安装的同名包。

**坑（工具箱）**：`plugin_manager` 不是每个会话都有——它和 `cordis_inspect_*`、
`cordis-plugin-development` 等技能一起出现，只在部分会话的工具箱里（和模型无关，
deepseek-flash、mimo 都有有两种情况）。没有这个工具的会话干不了安装，
设置 → 插件 页也只显示**已安装**的 bundle，新写的包在那里看不到。
解法：换个带 `plugin_manager` 的会话说一句“install_bundle 装 <绝对路径>”；
或在新建会话时带上插件开发技能入口。装完所有会话都能用，刷新页面即可。

## 升级后失效排查

**什么时候用**：官方更新后 pill 消失，或插件列表出现 failed。

1. 设置 → 插件：`@local/*` 行是否 failed（激活失败 = 依赖的服务没了或改名了）
2. 看界面：pill 消失但插件正常 = 槽位 id 变了；出现「改动统计失效」= 我们的路由没注册上
3. 用 `cordis_inspect_list` / `Service.listService` 对照 `inject` 里的服务名是否还在
4. 改完宿主代码，`remove_bundle` + `install_bundle`

**坑**：`priority: -1` 的覆盖注册在官方改 id 后表现为"多一条"，不会报错。

## 会话投影与计费时刻

**什么时候用**：写 `sessionProjections.register` 的 `apply`，要按时间分桶（峰谷、按日、按小时）。

- `assistant/message` / `assistant/attempt` 的 `event.time` 是**答完 / 采样**的时刻，不是请求发出时刻。
  跨 12:00、18:00 这类边界的长流式请求，按它分桶会落到错误的档。
- 要按发起时刻归段，监听 `step/start`：`{ type: 'step/start', time, data: { turn, step } }`。
  state 里存 `{ turn, step, at: time }`，后面同 `(turn, step)` 的样本用 `at` 分桶，缺失时回退 `event.time`。
- 新字段写成 `.nullable().optional()`，**不要升 `stateVersion`**：升版本会让宿主重建投影，历史桶全丢。
- `view` 只下发客户端要用的字段，内部锚点（如 `stepStart`）不下发。
- 验证：mock 一个 `ctx.inject` 收下注册项，直接喂事件序列，比开浏览器快。

## 会话删除类插件

**什么时候用**：要删除会话、清理会话文件，或做任何会改动 `~/.dsh/sessions` 的功能。

- 官方没有删除 API：`session-persistence-jsonl` 只有 create/open/stat/list，日志会一直累积。
  删除只能自己做，边界是：
  - `~/.dsh/sessions/<project>/<session-id>/`；子代理子对话按 header 的 `origin: 'subagent'`
    和 `parentSession` 递归收集，一起删
  - `~/.dsh/storages/session_projcache/sessions/<session-id>.json`
  - 工作区归属用 `workspace.detachSession(id)`；归档/置顶用 `workspaceRegistry.unarchiveSession` / `unpinSession`
  - 共享附件（content-addressed）和 spill 不动；`session-query-sqlite` 若启用，索引没有删除接口，会留残留
- 删除前必须拒绝：会话在 `ctx.sessions` / `ctx.agents` 里（正在使用），或
  `ctx.waterfall('workspace/session-activity', { sessionId }, () => Promise.resolve([]))` 非空
  （回合/子代理/后台任务/定时提醒）。这是归档用的同一个只读 seam，不用先归档
- 想确认没有别的进程在写，用 `sessionPersistence.open(id, 'write')` 拿写锁再删；
  `formatStatus === 'migration-required'` 的旧格式跳过这一步，避免打开时触发迁移
- 顺序：先 detach 工作区（此时 header 索引还认得它），再删文件；反过来 `detachSession` 可能找不到成员
- 删除成功后客户端要 `ctx.sessions.refresh()`，工作区 follow 帧不会通知会话文件消失
- **正在使用的会话**：宿主没有公开的释放接口。idle Agent 用内部 `agent.scope.dispose`
  （quiesce 版本，优先）或 `agent.scope.rawDispose` 释放（dispose 会关写句柄、注销 Agent），
  再轮询 `ctx.agents.get(id) === undefined`，然后照常删；`status: 'running'`、还有 pending inbox、
  或拿不到 disposer 时仍要排队。这是内部 API，官方升级后要复核——所以释放被拒时要**把原因写进队列**
  （`agent: running` / `inbox` / `no-dispose` / `dispose-threw: <msg>` / `still-registered`），
  否则 `pending.json` 里只剩一个 `agent`，查不出是哪条 seam 变了。
  `still-registered` = dispose 跑完了但登记表里还有同 id 的 Agent（客户端又把它 resume 回来了），
  所以释放要**循环几轮**（dispose → 轮询 1s → 再来），单轮放弃就等于永远排队
- 旧做法（只能排队）：写句柄被占，同一进程删不掉。
  做法是先归档隐藏，把 id 写进 `<DSH_HOME>/storages/session-delete/pending.json`，
  下次启动、Agent 恢复前 purge；重启前取消归档 = 取消删除。队列文件原子写、0600，
  坏文件隔离成 `.corrupt-*`，不静默丢
- 删除前先 `ctx.parallel('workspace/session-stop')`：定时提醒也算
  `workspace/session-activity`，不停掉的话，带提醒的闲置会话永远删不掉
- 启动 purge 延时跑（默认 1.5s），避开 profile/registry 初始化；逐条处理、逐条删队列项，
  不要整体重写，避免和同时在跑的新删除请求互相覆盖
- 关窗口/刷新页面**不会重启 Host**：队列只在 Host 启动时跑。补一个 `/api/session-delete.purge`
  路由 + 页面加载调用 + 每分钟重试，用户“重进”页面时也能清掉；彻底退出仍是最可靠的方式
- 会话删除时一并删 `<DSH_HOME>/undo/sessions/<id>`（见下节）；删旧会话不留快照

## 会话撤回

**什么时候用**：做会话撤回、从某个切点继续聊，或给用户消息加操作。

- **不要做文件快照/文件恢复/恢复前副本**：用户明确不要文件恢复。预检只 `observeSession`
  读一次事件，返回轮数/消息/token/切点/是否第 1 轮/被撤用户消息；不扫工作区、不读 state
- 撤回 = `ctx.sessions.fork({ sessionId, atSeq: 切点 })`，切点取目标轮 `turn/start.seq - 1`；
  第 1 轮没有前缀，改为 `uiWorkspace.startSession()`
- 被撤消息放回输入框：唯一正常路径是打开后
  `conversation.input.requestDraftInitialization(binding, { prompt, clearPreviousDraft: true })`
  （返回 `applied` / `preserved` / `blocked`，`blocked` = 正在提交，要重试）；
  `blocked` 或 seam 不在时才写 `localStorage['dsh.conversation.<childId>']` 的 `draft` 兜底。
  **两份都写会互相打架**：这个 key 就是官方输入框自己的草稿存储（`createConversationStore` /
  `readConversationDraft`，挂载时读一次），手写一份再被 store 覆盖/清除，容易留下
  “发出去的消息又出现在输入框”。第 1 轮用 `startSession(undefined, { prompt })`
- fork 会复制切点之前的 `goal/change` 事件，旧目标会跟着进新会话；打开后
  `ctx.remote.goals.clear(sessionId, { id, revision })` 清掉（inject `remote`、`remote.goals`）。
  **`complete` 的也要清**：漏掉这一种，新会话顶部就还挂着被撤内容当目标
- fork 的 seed 连**待发队列**一起复制（`agent/inbox/spliced` 的插入事件在切点之前）：
  被撤回合那条排队消息会跟着进新会话，自己跑起来。撤完要按队列 UI 的同一 seam 清掉：
  `ctx.sessions.scope(childId).get('conversation').updateQueue(itemId, { kind: 'remove' })`，
  item id 从 `binding.session.projections.faceOf('inbox')` 的 `next-turn` / `next-step` 取。
  排队里的 `/goal …` 命令被复制过去重跑，就是“撤回完又自动建了目标”的来源
- `user/message` 事件的 `data.turn` 可能是空；取目标轮用户文本要按 `turn/start` 的 seq 到
  `turn/end`/下一轮之间找 `source.kind === 'user'` 的第一条
- 旧会话删除复用 `session-delete` 的队列：fork 后调用它的删除路由，live 会话先归档排队。
  路由对排队返回 **202 + `queued: true`**，不是失败也不是完成：前端必须读 body，
  排队时提示“下次启动删”，别把 202 当成功（否则界面说已删、文件还在）
- 官方**用户消息操作行没有 slot**（复制按钮写死在 `UserMessageNodeView`）：要放到复制右侧只能
  DOM 注入——克隆复制按钮的 `className`、`currentColor` 图标，靠 `MutationObserver` 重挂；
  `turn` 从最近的 `[data-chat-turn]` 取，`sessionId` 优先沿 React fiber 往上找
  `props.sessionId`，再 fallback `sessions.list` 的 `retainedBy.mainView`
- `conversation.chat.turnTail` 的 `turn` 是 **Turn 对象**；取 `turn.turn`
- 删除会话后要清客户端 `localStorage` 的 `dsh.workspace.view.v5` 里残留的 session id，
  否则会留下“未分组”空行，点删除还会报“会话不存在”

## 会话行菜单与客户端槽位

**什么时候用**：给侧栏会话的「…」菜单加操作。

- 槽位 `sidebar.workspaces.session.menu.item`，配弹窗用 `shell.overlay`；注册带 `locale: NS` 才会拿到 `t`
- 每项用原生 `MenuItemButton`（内部就是 `role="menuitem"` 的 button）；`useMenuOpenState()` 由槽位声明注入，点击后先 `setMenuOpen(false)`
- 客户端动作走宿主 `ctx.connection.fetch.register({ path: '/api/...', methods: ['POST'], requestBody: 'buffered', fetch })`，
  页面用相对路径 `api/...` 调，借鉴权通道；不要用裸 `webServer` 路由做破坏性操作
- Desktop 的 app.asar 里没有 `@deepseek-ai/dsh-client-ui-primitives` 包目录，但 Module Loader 把它作为
  baseline external 直接给 `factory(require)`：`Button`、`MenuItemButton`、`Modal`、`Toast`、`Icon*` 都能取到。
  菜单行/弹窗/提示优先用这些原生组件，悬停、按下、焦点和尺寸才和宿主一致；自己仿样式容易对不上
- 动态 `cordis-client-runner` 沙箱里没有 `require`，那条路才需要自绘
- `shell.overlay` 整层 click-through；原生 `Modal`/`Toast` 会自己 portal 到 body，不用自己管 backdrop
- 删除后 `ctx.sessions.refresh()`；当前主视图被删时再 `ctx.uiWorkspace.startSession()`；
  其他标签页用 `BroadcastChannel` 通知后同样 refresh
- `conversation.chat.turnTail` 的 `turn` 是 **Turn 对象**，不是数字：取 `turn.turn` 再发给宿主，
  否则会收到 “turn is missing or malformed”
- 反查当前 sessionId：优先沿复制按钮的 React fiber 往上找 `props.sessionId`，再 fallback
  `sessions.list` 的 `retainedBy.mainView` / `uiWorkspace.mainReference`
- 官方**用户消息操作行没有 slot**（复制按钮写死在 `UserMessageNodeView`）：要放到复制右侧只能
  DOM 注入——克隆复制按钮的 `className`、`currentColor` 图标，靠 `MutationObserver` 重挂；
  `turn` 从最近的 `[data-chat-turn]` 取，`sessionId` 从 `sessions.list` 里 `retainedBy.mainView > 0`
  的行取，fallback `uiWorkspace.mainReference`。官方 DOM 一改就会失效，属于兼容补丁
- 删除会话后要清客户端 `localStorage` 的 `dsh.workspace.view.v5` 里残留的 session id
  （`sessionOrderByAccount` 各数组），否则会留下“未分组”空行，点删除还会报“会话不存在”
- 验证：槽位 inspector 能看到注册项就算客户端半加载成功；视觉仍要在页面上看，无浏览器控制时只能报告未验证

## 外观：配色、表面与品牌

**什么时候用**：改界面颜色、换品牌主色、给某个区域单独上底色，或改品牌名 / 标语 / 图标。

### token 的权威位置

- 颜色表在 `@deepseek-ai/dsh-client-ui-theme/lib/client.js`，运行期注入，不是独立 css 文件；
  asar 里 `dsh-web-frontend/dist/assets/index-*.css` 只管布局，查颜色别去那里。
- 三截分工：`--dsw-static-*` 是色阶（定义在 `:root`），`--dsw-alias-*` 是语义别名（定义在
  `body` 和 `body[data-ds-dark-theme]`），`--dsh-*` 是尺寸/字体/滚动条。改语义色改 alias，
  改整套色系改 static 色阶。
- **自定义属性里引用 alias token 时，声明必须挂在 `body` 上（或更深的祖先），不能挂 `:root`**：
  `:root` 只拿得到 `--dsw-static-*`，alias 是在 `body` 上才出现的；`--sm-x:color-mix(...,var(--dsw-alias-…))`
  写在 `:root` 里会整条失效，所有 `background:var(--sm-x)` 全部退成透明（表现为“底色突然都没了”，
  而且报错都不报）。稳妥写法是声明放 `body{…}`，同时在使用处带内联兜底
  `background:var(--sm-x,color-mix(in srgb,var(--dsw-alias-…) 7%,transparent))`。
- **弹层底色有两层名字，覆盖时要一起写**：公共菜单走 `MenuSurface`，读的是
  `--dsw-menu-surface-fill`（浅 `#f8f9fa94` / 深 `#43454a73`）；`--dsw-specific-menu`
  （darwin 下 `#f8f9faf0` / 深 `#303136f0`）只是它的别名，队列面板、上下文面板、统计面板这些老面板在用。
  **侧栏左下角的账户菜单属于前者**（官方 README 明确写了 “Shared menus use `--dsw-menu-surface-fill`
  and blur through `MenuSurface`；platform code must preserve those token values”），
  所以只覆盖别名时「调菜单没反应」——这是踩过的坑。外观页的「菜单 / 弹层」现在两个 token 一起下发，
  一改的话账户菜单和各面板会同时变（官方没给它们各自的旋钮）。
  注意它**不在** `base` / `bg-layer-1` 的引用链上，所以调「对话区」「卡片」不会影响菜单。
- **浮层不止一套材质：MenuSurface 系和 HoverCard 是两码事**。账户菜单走 `MenuSurface`
  （`background:var(--dsw-menu-surface-fill)` + `backdrop-filter:var(--dsw-menu-backdrop-filter)`）；
  **文件区 / 工作区 / 会话行悬停出来的卡片是 `HoverCard`**，自己写死了
  `._card_38jqx_9{--dsw-hovercard-bg:#2C2C2E;background:var(--dsw-hovercard-bg);box-shadow:var(--dsw-shadow-lv3)}`
  —— 深灰实色、没有模糊，而且这个变量全 asar 只有这一处定义、任何主题都不覆盖，
  所以浅色主题下悬停卡片也是深灰。
- **账户菜单的“不透明”来自一层背衬，不是它自己**：darwin 上 MenuSurface 会额外 portal 一个
  `[data-menu-backing]` 到 body，
  `html[data-platform=darwin] ._backing_ri079_2{position:fixed;z-index:-1;background:var(--dsw-alias-bg-base)}`
  （非 darwin `display:none`）。所以菜单看起来实心，是那块 `bg-base` 把后面挡住了；
  `backdrop-filter` 模糊的也只是这块纯色底，视觉上等于没有。
  **只搬 `--dsw-menu-surface-fill` 到别的浮层，结果是半透明透出内容、字看不清**——踩过。
- 统一的做法（skin 的 `OVERLAY_RULES`）：变量是组件自己声明的，从 body 写内联压不过，
  用规则抬 specificity，把**两层一起**塞进 background（多背景第一层在上、只有最后一层能带颜色）：
  `html[data-ys-overlay-unified] [class*="_card_"][class][class]{
  --dsw-hovercard-bg:linear-gradient(var(--dsw-menu-surface-fill),var(--dsw-menu-surface-fill)),var(--dsw-alias-bg-base)}`
  这样和官方 backing 同源（用户把对话区调透明时两边一起变），也就不用做模糊了。
  **背景一改，文字必须一起改**：卡片的文字是照着深灰底写的浅色，只换背景会白字浅底、
  看不清（踩过两次）。所以同一条规则里把 `color:var(--dsw-alias-label-primary)` 拉回来，
  并给子元素 `color:inherit`（内容里有些行是写死的浅色）。
  另外「改动文件预览」是另一个变体 `_preview_38jqx_52`（`bg-layer-1` + 自带 color），
  本来就不透明、文字也对，别顺手改它。
  同样带 `_card_` 的 markdown 代码块（`_card_1pq26_1`）读的是
  `--dsw-alias-markdown-code-block`，不受影响。开关 `data-ys-overlay-unified` 默认挂上。
- **tooltip 是第三套**：`--dsw-alias-tooltip-bg`（`neutral-bluish-750/850`，深色键帽），
  官方故意和菜单区分，没跟菜单统一，别顺手改。
- **对话区里的 Markdown 块是另一套 token，别和 `bg-layer-*` 混**：
  代码块 `--dsw-alias-markdown-code-block`、代码块顶部语言条 `--dsw-alias-markdown-code-block-banner`、
  行内 code `--dsw-alias-markdown-inline-code`（另有 citation / tag / placeholder / code-segment-* 几个边角）。
  Shiki 的 `--shiki-background` 也指向 `code-block`，所以覆盖它连高亮块的底色一起生效。
  外观页把它们拆成三项，命名跟「已编辑文件（头行）/（文件行）」一致：
  「代码块（主体）」= code-block、「代码块（语言条）」= code-block-banner、「行内代码」= inline-code。
  三者的真实锚点（2026-10 版前端）：
  - 行内代码：`._markdown_1ypvv_5 :not(pre)>code{background-color:var(--dsw-alias-markdown-inline-code)}`
    —— 官方唯一使用点，`background-color` 之外还有 `.5px solid border-l1` 的边框和圆角，看起来是“小胶囊”。
  - **没有语言名的围栏块走另一条渲染分支**：`k && P===void 0 ? 高亮 HTML : <pre class="…_plain">`，
    plain 那个 `pre` **没有任何背景**，露出的是容器 `.md-code-block` 的 `background-color: bg-base`。
    所以只覆盖 `--shiki-background` 时，“写着「代码块」的那种块”主体不动——用户就是据此发现的。
    补法是给稳定类名 `md-code-block` 兜一层（**只在调过这一项时才生效**，否则默认会被改成 code-block 色）：
    `html[data-ys-code-block] [class*="md-code-block"], html[data-ys-code-block] [class*="md-code-block"] pre{background-color:var(--shiki-background)}`，
    开关由 `applySurfaceFlags()` 按 `look.surfaces[id]` / `look.alphas[id]` 有无来加删。
  - 代码块主体：Shiki 渲染，元素上是内联 `style="background-color:var(--shiki-background)"`，
    而 `:root{--shiki-background:var(--dsw-alias-markdown-code-block)}`。所以想让主体只影响代码块，
    覆盖 **`--shiki-background`** 而不是 `alias-markdown-code-block`。
  - `--dsw-alias-markdown-code-block` 官方 22 处引用（工具输出块 `HXUrla_output` / `B9WI8q_body`、
    turn trigger、搜索面板…），直接覆盖它等于“一处改、多处变”，这也是外观页把它单独拆成
    「工具输出块」一项的原因。
  **浅色主题下 code-block 与 banner 取值相同**（都是 `neutral-bluish-50`），所以只调其中一个时另一个
  “看起来没变”是对的；深色才是 `-900` / `-850` 的差别。另外 `code-block` 官方有 22 处引用
  （工具输出块、turn trigger、搜索面板…），想让“主体”只影响高亮块就改写成 `--shiki-background`。
  **语言条的 `code-block-banner` token 是死的**：真实渲染里语言条外层是 `_bannerWrap`（`background-color:
  var(--dsw-alias-bg-base)`），内层 `[data-code-block-banner]` 自己**没有背景**，那个 banner token 只被
  dsl 那套 `.banner` 规则引用、聊天里走不到 —— 所以覆盖 token 毫无反应，表现为“调主体语言条跟着变
  （因为它是透明的），调语言条什么都不发生”。正确做法是直接给元素上背景：
  `html[data-ys-code-banner] [data-code-block-banner]{background:var(--ys-code-banner)}`，
  由 `applyPaintVars()` 按 `look.paint.codeBannerColor` 决定加不加开关。
  **而且外层 `bannerWrap` 也得覆盖**：真实结构是 `bannerWrap`（`background-color: bg-base`）> 内层
  `[data-code-block-banner]`，内层经常没有背景，只染内层会露出外层的 bg-base，看起来“调了没变”。
  规则写成两行：`[data-code-block-banner]` 与 `:has(> [data-code-block-banner])`（后者命中那个直接父级，
  不用知道 hash 类名）。**但外层只能设 `transparent`，不能也涂同一个色**：两个半透明层叠起来的浓度是
  `1-(1-α)²`（α=15% 时约 28%），头行会比代码区明显重 —— 半透明面一律只涂最里面那一层。
  同理，任何“看起来头重脚轻”的卡片，先怀疑自己给父子两层都上了同一个半透明色。另外**这一项必须先选颜色**：未选色时 `tinted()` 返回 null、变量不写、规则不生效，
  只拖透明度不会有任何变化（语言条本来就没有自己的底色）。

  「行内代码」（inline-code）—— 语言条和主体是两条 token，想分开调就必须分开建目标。
  **调「卡片」对代码块无效**，这是很容易踩的错判。
- **「已编辑文件」卡片（`data-changed-files`）的变量改不到**：头行底色 `--changes-fill`
  是组件在自己的 `.card` 规则里**声明**的（`--changes-fill:var(--dsw-static-neutral-50)`，深色在
  `body[data-ds-dark-theme] .card` 再声明一次），自定义属性在声明元素上就定值了，
  **从 body 写内联变量压不过它**（继承值 < 元素自身声明）。文件行更是完全没有底色（`background:0 0`），
  hover 才用 `--dsw-alias-interactive-bg-hover`。
  做法：带开关的规则 + 三重属性抬 specificity —
  `html[data-ys-changes-head] [data-changed-files][data-changed-files][data-changed-files]{--changes-fill:var(--ys-changes-head);--changes-hover:var(--ys-changes-head)}`
  （三重是为了压过深色主题那条 `body[data-ds-dark-theme] .card`），文件行则是
  `html[data-ys-changes-row] [data-changed-files] [class*="_row"]{background:var(--ys-changes-row)}`。
  两个开关都由 `applyPaintVars()` 按 `look.paint` 有无来加/删，没设时规则完全不生效。
- **输入框 / 用户消息气泡的包边阴影直接复用工作区卡片那套变量**（`--sm-frame` / `--sm-frame-lift` /
  `--sm-frame-shadow`），这样四处始终一致，改描边色时输入框、气泡、工作区卡片一起变：
  `html [class*="_bubble"], html [class*="composerSeat"] [class*="_card"]{box-shadow:
  var(--sm-frame-lift,…), var(--sm-frame-shadow,…), inset 0 0 0 1px var(--sm-frame,…)}`。
  `html ` 前缀是必需的：气泡的官方类名和我们同 specificity，不抬一级会看注入顺序。
- **包边与阴影**：几何写死在规则里，颜色/浓度给变量 ——
  `box-shadow: 0 6px 18px 0 var(--ys-X-shadow,transparent), inset 0 0 0 .5px var(--ys-X-border,transparent)`。
  **包边一律用 `inset` 画**，别用 `border`：border 会把盒子撑大（气泡宽度、输入框高度都会跳）。
  锚点：气泡 `[class*="_bubble"]`（官方只有 3 个类名、没有容器叫 bubble，安全）、
  输入框 `[class*="composerSeat"] [class*="_card"]`、侧栏 `[class*="sidebarCol"]`。
  一组变量共用一个开关（`data-ys-bubble` / `data-ys-composer` / `data-ys-sidebar-shadow`），
  任一有值才开，缺省时那一层是 transparent，等价于不画。
- **交付文件卡片（`[data-presented-file]`）同理**：底色来自 `--deliverable-fill`，声明在
  `Deliverables_module_css.css` 的 `.root` 上（深色在 `body[data-ds-dark-theme] .root` 再声明），
  祖先写变量压不过；直接给 `[data-presented-file]` 上 `background-color`，`[data-presented-file][data-presented-file]`
  双属性是为了压过它自己的 `:hover`（`--deliverable-hover`）。
  `data-presented-file` 是官方稳定属性，比 `_file` 里的 hash 可靠。
- **paint 目标也能有透明度**：`PAINT_TARGETS` 里标 `alpha: true`，外观页就会给它出滑条
  （判定在 `alphaKey = token || (paint && alpha) ? target : null`，`TARGETS` 构造时要透传 `alpha`）。
  折法在 `applyPaintVars()`：`color-mix(in srgb, <色> <alpha>%, transparent)`，只在 `alpha < 100` 时包一层，
  等于 100 就写原色（省一层嵌套）。**没选颜色时拖透明度不会有任何效果**（尤其“文件行”这种默认
  `transparent` 的项，透明乘透明还是透明），这一点要跟用户讲清楚。
- 常用三个：侧栏整列 `--dsw-specific-sidebar-fill`（浅 `#f9fafb` / 深 `#1b1b1c`）、
  主列 `--dsw-alias-bg-base`（浅 `#fff` / 深 `#151517`）、抬升面 `--dsw-alias-bg-layer-1..3`。
- 界面里所有蓝都锚在 `--dsw-static-deepseek-500`（`#4176e6`，深色档位走 `-400` `#7aaaff`）；
  焦点环、链接、选中态、info 按钮都是 `var()` 转发，**改色阶一处，全站跟着走**。
  `--dsw-alias-brand-primary` 不是蓝，它指向 `label-primary`（黑白），别改错。
  `--dsw-static-blue-*`（`#3b82f6` 那套）只给文档选区用，跟品牌色是两条线。

### 覆盖方式

- 唯一正路是 `ctx.theme.overrideTokens(source, tokens)`，`tokens` 形如
  `{ '--token': { light, dark } }`，同一 source 再调一次会**替换**旧层（旧 disposer 变 no-op）。
  ui-layout 把快照写成 `body` 的内联变量，优先级压过内置样式表。
- 内置 light/dark 主题的 `tokens` 是空对象，颜色全在 css 里 —— 所以「没有覆盖层」等于官方原样。
  想还原默认就 dispose 掉自己的层，别写一套和官方等价的覆盖值（浮点差异会让默认态偏色）。
- 也可以 `ctx.theme.register({ id, colorScheme, tokens })` 注册整套第三方主题，但要先改设置里的
  `preference` 才会激活；只换色不换主题 id 时用 `overrideTokens` 更省事。
- 服务不在就静默跳过（`ctx.inject(['theme'], ...)` 里拿不到就不做），别写进 `inject` 声明，
  否则 ui-theme 被禁用时整个插件在设置里显示 failed。

### 外观中心的结构

- 一份 `look` 状态（`lead` / `tail` / `slogan` / `icon` / `seed` / `surfaces`）存在
  `localStorage['dsh.skin.look']`，配一个「写入即通知」的极简 store（`Set` 存 listener，
  `useReducer` 强制重渲染）。品牌位组件和设置页读同一份，改哪边都即时同步。
- **每个目标都要有一句“会影响什么”的说明**：`DICTS` 里 `look.hint.<目标 id>`（中英各一条），
  直接渲染在目标行里（`.ys-pal-targetHint`），不用点开就能对比 —— 所以目标不是胶囊而是**列表行**：
  `[色块] 名称 …… 一句说明`。加目标时 hint 是必填项，漏了界面上会直接显示 key 本身。
  说明的写法是“影响哪里”，不是“这是什么” —— 用户靠这句话判断该调哪一个。
  名称列 `min-width:108px` 固定宽度，说明列 `flex:1` 自动换行。
- **调节区跟着目标走，不放在页面底部**：每个目标是「列表行 + 展开区」的手风琴，
  点一行在它下面展开（色域图 / 色值 / 浓度 / 透明度 / 恢复这一项 / 主色的派生色阶），
  再点同一行收起（`setTarget(item.id === target ? null : item.id)`，`target` 允许为 `null`）。
  实现要点：`targetById(null)` 会回落到 `TARGETS[0]`，所以收起时那些按 `target` 算的派生值不会炸；
  **但色域图的 `ResizeObserver` 测量 effect 和逐像素绘制 effect 的依赖里必须带上 `target`** ——
  展开区是重新挂载的，canvas 换了新元素，不重跑就会画出空白（以前面板常驻，`[]` 依赖看不出来）。
  展开区的底色用 `label-primary` 4%，跟列表行 hover/选中区分开。
- 外观页的胶囊**按界面分区排**：`TARGET_GROUPS`（主色 / 侧栏 / 对话区 / 输入区 / 弹层 / 品牌）决定分组与顺序，
  `GROUP_OF` 决定每个目标归哪组，`TARGET_ORDER` 决定组内顺序。加目标时**三处都要补一行**——
  只加 `SURFACES`/`PAINT_TARGETS` 而忘了 `GROUP_OF` 会静默落到「对话区」，忘了 `TARGET_ORDER`
  则排到该组末尾（`indexOf` 返回 -1 会跑到最前）。
- **哪些面会跟主色走，取决于它读哪个色阶**：`--dsw-static-deepseek-*`（品牌）才联动，
  `--dsw-static-neutral*` / `neutral-bluish*`（中性）不联动 —— 官方就是这么分的。
  所以气泡（`deepseek-50`）跟主色，而代码块 / 工具输出块 / 行内代码 / 已编辑文件（都是 neutral 档）
  改了主色也不动。**再加上一旦用户单独给某个面设过色，`user ?? fallback` 里 user 优先，就永远不动了。**
- 想联动就开 `look.follow`（外观页「内容面跟随主色」）：`fallbackFor()` 在未单独设色的内容面上
  混入 10% `--dsw-static-deepseek-400`（`bubble` / `code` / `toolOutput` / `inlineCode` 标了 `follow: true`）。
  已单独设过色的面不受影响（仍以用户值为准），要恢复跟随得先点「恢复这一项」。
  `changesHead` / `changesRow` 是 paint 目标（写 `--ys-*`），没有深浅两套值，暂不参与 follow。
- 表面是可枚举的表：`[{ id: 'sidebar', tokens: ['--dsw-specific-sidebar-fill'] }, ...]`。
  **表里的 token 不必是官方的**：`overrideTokens` 写的是任意的 body 内联变量，所以别的插件声明在
  `body` 上的自有变量也能当“表面”来调 —— 外观页的「工作区卡片」/「工作区卡片描边」就是
  sidebar-marks 的 `--sm-frame-fill` / `--sm-frame`。fallback 要写成和那个插件默认值**等价**的字符串
  （例如 `color-mix(in srgb,var(--dsw-alias-label-primary) 5%,transparent)`），这样没调过时零变化；
  透明度本来就会再乘一层 `color-mix(… X%, transparent)`，不要再自己加百分比。
  **fallback 必须是纯色**：如果 fallback 写成 `color-mix(label-primary 5%, transparent)` 这种“预混好浓度”的值，
  滑条拖到 100 也只有 5%——用户会以为上限被写死。正确做法是 fallback 写 `var(--dsw-alias-label-primary)`
  这类纯色，把出厂浓度放进 `ALPHA_DEFAULT`。**外观页下线后这个表只剩三项**
  （`{ sidebar:40, groupCard:5, groupEdge:22 }`）：行底色改成 sidebar-marks 自己写死
  （选中 85%、运行中/完成未读 45%），气泡改成 skin 写死 85%。
  当滑条默认值，这样 0–100 就是真实的 0–100%，拖满是实色。
  侧栏两档行底色也这么接进来了（「当前对话底色」=`--sm-open-fill`、「运行中 / 完成底色」=`--sm-run-fill`，
  完成未读读的是同一条变量，所以一个目标管两种状态）；**改 sidebar-marks 的默认浓度时，要同步改
  skin 里那两个 fallback 常量（`ROW_OPEN` / `ROW_RUN`）**，否则一开外观页就会跳回旧浓度。
  另外用户在外观页只拖颜色不拖透明度时，写进去的是纯色（100%），行会变成实底 —— 想保持“淡”的观感，
  要连透明度滑条一起给。
- **有的面默认就该是半透明**：滑条只下发“用户拖过”的值（`look.alphas[id]` 存在才算），所以给表面表加
  `alphaDefault` 字段（气泡 = 60），`applyLook` 里用 `look.alphas[id] ?? surface.alphaDefault ?? null`。
  否则默认态还是官方实色——把默认值写在 `ALPHA_DEFAULT` 里只改了滑条显示，界面纹丝不动。
  **加一个新区域 = 加一行**，设置页的目标胶囊、覆盖逻辑、恢复逻辑全都自动有；不要为每个
  区域写一份组件。
- 一次 `overrideTokens` 里同时下发色阶和所有表面覆盖；没改任何东西时**不写层**，
  这样默认态和官方像素级一致。改外观时先 dispose 旧层再建新层。
- 表面没覆盖时，UI 里显示主色并标注「跟随默认」，一旦拖动就写入该表面的覆盖值；
  「恢复这一项」= 从 `surfaces` 里删掉这个 id。
- 品牌名 / 标语 / 图标同样走 store：`Mark`/`Name` 用 `useLook()` 取，`rewriteSlogan`
  用全局 `look` 读，改完要把旧标语文本替换掉（`syncSloganText` 记住上一句再替换）。

| 对话区 | 已编辑文件（头行） | `--ys-changes-head`（paint） | `[data-changed-files]` 卡片的 `--changes-fill` / `--changes-hover` |
| 对话区 | 已编辑文件（文件行） | `--ys-changes-row`（paint） | 卡片里每个文件行（官方本来无底色） |
| 输入区 | 输入框 | `--dsw-specific-input-major` | 输入卡片；输入框下方 dock 卡片也复用它 |
| 输入区 | 输入框上渐隐 | `--ys-seat-alpha`（仅透明度） | composerSeat 的 36px 渐变遮罩 |
| 弹层 | 菜单 / 弹层 | `--dsw-menu-surface-fill` + `--dsw-specific-menu` | 账户菜单、上下文 / 队列 / 统计面板（两个变量必须一起写） |
| 品牌 | 图标 | `look.paint.iconColor` | 侧栏标志 + favicon |
| 品牌 | 名称·前段 / 后段 | `look.paint.leadColor` / `tailColor` | 品牌名两段 |

**透明度**：token 面都有滑条（折进值里）；`alpha: true` 的 paint 项也有（`color-mix(<色> X%, transparent)`，
**必须先选颜色**）；`alphaOnly` 的项只有滑条、不参与配色。

### 透明度：侧栏和对话区

- macOS 上这两块是**半透明压在原生 vibrancy 上**的：`[data-platform=darwin] .frame{background:0 0}`，
  所以下面透出的是 Electron 的窗口毛玻璃（`vibrancy: "sidebar"`，`backgroundColor: #00000000`）。
  侧栏实际是 `color-mix(sidebar-fill 97%, #7a9bf0) 40%`（深色 50%）+ 一条 `#7a9bf0 → #8f89b8`
  的竖向渐变；对话区是不透明的 `bg-base`。
- 透明度改不成 CSS 变量（官方那条 40% 硬编码在 hash 类名的规则里），但可以把整条规则重写一遍：
  选择器用 `[class*="sidebarCol"]` —— CSS modules 的类名是 `hash + local 名`，local 名稳定，
  **不需要知道 hash**。重复三次属性把 specificity 抬到 (0,5,1)/(0,6,2)，压过官方的 (0,2,0)/(0,3,0)，
  不用 `!important`。
- **对话区不止两层**：外层 `centerCol`、里面 `ConversationRoot`，中间还可能有容器，
  每一层都吃同一个 `bg-base` 且不透明，只调最外层会被挡回去。定位不能靠"最高的直接子"
  （层叠层数不固定），要**从会话内容往上走**：`document.querySelector('[data-chat-turn], [contenteditable="true"]')`
  然后沿 `parentElement` 找，凡是 `getComputedStyle(node).backgroundColor === bg-base 的计算值`
  就收下，整条链路都打标记。bg-base 的实际颜色用一个临时 `<span>` 读出来比对。
- **输入框那排信息是 `[data-composer-dock]`**：官方 InputBar 的 `.dock`（flex + `justify-content:center`
  + `gap:12px` + `padding-top:4px`），里面是 `conversation.composer.dock` 槽位（usage-cost 的 pill 等）
  和 `ContextMeter`（有 activity 时隐藏）。**要挪位置不用动 DOM**：InputBar 的 root 是 `flex-direction:column`，
  给 dock 加 `order:-1` 它就跑到输入卡片上方（官方结构一改自然回落），`order:0` 即回到下方。
  包成卡片时：**宽度自适应内容**（`width:fit-content`，官方本来就跟着内容走；撑满 `width:100%` 会显得太宽，
  用户明确否掉）、`border-radius` 只留远离输入框那一侧的圆角、**别动 margin**（它靠 composer 的负 margin
  贴着输入卡片）；`:not(:empty)` 收掉空状态。
  **底色/透明度直接复用 `--dsw-specific-input-major`**（外观页「输入框」那一项的 token，ui-layout 写成 body
  内联变量），调输入框就一起变，不要另开一项或写死 15% 之类的混合色。
  **“像从输入框里长出来”的反圆角**：卡片贴输入卡片的那条边与它齐宽相接，贴边那一侧的两个角各放一个
  `--ys-dock-radius` 见方的 `::before/::after`（`left/right:calc(-1 * …)`，`top:0` 或 `bottom:0` 取决于在上还是在下），
  背景用 `radial-gradient(circle at 0% 100%, transparent R, <fill> R)`——卡片在下方时圆心取「贴卡片那一侧的
  下角」；移到上方后改成 `at 0% 0%` + `bottom:0`，整个形状上下翻转。
  圆心在贴边角上，距离 ≤R 透明、外圈才是底色，画出来就是从卡片竖边弯进贴边的小弧，
  正好补掉输入卡片圆角外侧那块空隙。伪元素必须和卡片同色（共用变量 `--ys-dock-fill`），
  否则半透明会叠出深一块。
  另外**上移（负 margin）必须给输入卡片补等量 `padding-bottom`**：`-8px` 把 dock 压进卡片时，
  会把编辑区底部盖住、光标直接看不见。现在两处共用 `--ys-dock-lift`（挂在 composerSeat 上），
  dock 用 `margin-top:calc(-1 * var(--ys-dock-lift))`、卡片用 `padding-bottom:var(--ys-dock-lift)`，
  dock 只是填进让出的空档，视觉贴住但不再遮挡。
  注意 `conversation.input.dock` 是另一个槽位（任务面板在那），它渲染在 inputBar **上方**、而且官方
  自己就是卡片（`--dsw-specific-menu` + 阴影），别当成同一排去包。
- **输入框上方那块“雾”不属于对话区背景层**：会话页 `[data-phase=active]` 时，`.composerSeat` 自带一条
  `linear-gradient(180deg, bg-base 0, bg-base 36px)` 的渐隐遮罩（滚动内容从输入框后面滑过时被它压住）。
  它是 `background-image`，`backgroundColor` 仍是 `transparent`，所以“从会话内容往上收集
  `backgroundColor === bg-base` 的层”那套永远收不到它——调对话区透明度时它原地不动，用户会问
  “输入框附近这块是什么”。做法是**单写一条规则**：
  `html[data-ys-seat][data-platform=darwin] [data-phase=active] [class*="composerSeat"]`（另加
  `[data-content-phase=active]` 变体），渐变末端用 `var(--ys-seat-alpha,100%)`。
  选择器必须带 `[data-phase=active]`：空会话（hero）时官方本来没有这层背景，无条件加会多一条底部色块。
- **这条雾带算独立一项**：用户先要求它跟对话区一起变透明，随后又要“单独调节”——它在表面表里是一条
  `alphaOnly` 行（`tokens: []`，不参与配色），外观页里只给透明度滑条、不画色域图，存 `alphas.seat`，
  开关 `data-ys-seat`、变量 `--ys-seat-alpha`，不设置时 100%=官方原样。加这种“只调透明度”的区域
  就往 `SURFACES` 加一行 `alphaOnly: true`，构造 `TARGETS` 时要把 `alphaOnly` 透传过去
  （漏了就退化成普通色面，色域图会白出一块）。
- **透明度要跟着会话切换重挂**：主列内容会在切会话/冷启动时重建，`[data-ys-chat-main]` 标记随旧节点
  一起消失，表现就是“切一次对话，对话区又变回官方不透明”。做法是 `watchChatLayers()`：观察主列
  `childList`（rAF 合并），只在“缓存为空或缓存节点 `isConnected === false`”时重跑
  `markChatMain()` + `applyAlphas()`——流式输出只改文本、节点还在，所以不会反复重跑；
  冷启动再补一次 1.5s 延迟重试（shell 还没挂载时第一次必然空手）。
- **重收集前必须先撤旧内联**：`markChatMain` 判断的是“计算背景 === bg-base”，而上一轮写进去的
  `background` 会让这些节点算出来是半透明渐变、不再等于 bg-base，结果被自己排除、掉出缓存，
  来回切会话时透明度就会时有时无。所以重收集的第一步是把 `[data-ys-chat-main]` 的内联背景和标记
  全部清掉，再重新判定。
- **这几层的透明度用内联样式压**：CSS 规则会被更深的官方规则盖住，而
  `node.style.setProperty('background', …)` 优先级最高；颜色串里写 `var(--dsw-alias-bg-base)`，
  所以浅深切换照样跟着变。定位结果缓存（`chatNodesCache`），拖滑条时不重跑 DOM 遍历。
- **非 pane 表面的透明度直接折进 token 值**：官方每一处读到的都是 `color-mix(in srgb, <色> X%, transparent)`，
  不用覆盖任何规则。浅深两色各自乘同一个 alpha；用户只调透明度不选色时，用表里记的官方默认值当底色。
- **规则要加开关**：`html[data-ys-sidebar]` 存在才匹配，没调过就完全不生效。
  否则会顶掉系统「降低透明度」（`prefers-reduced-transparency: reduce`）时官方的降级规则。
- 规则加 `data-platform=darwin` 前缀：Windows 下侧栏本来就是纯色，跟着变透明会破相。
- 变量默认值写官方数（`var(--ys-sidebar-alpha,40%)` / `,50%)` / chat `,100%)`），即使规则一直挂着，
  没设置时视觉也和官方一致。

### 不要给面加渐变

**什么时候读**：想“让某几个面看起来像一个系统”的时候。

- 曾经把官方侧栏（`[data-platform=darwin] .sidebarCol`）那串竖向蓝紫渐变抽成常量，套到气泡、输入框、
  代码块上，还配了个 `look.fx` 开关。**用户的结论是“侧栏并没有渐变”，全部撤掉了。**
  原因：那串渐变只在 `[data-platform=darwin]` 且官方那条规则命中的场景可见，用户日常看到的侧栏
  就是纯色 + 半透明；拿一个看不见的东西当“统一形式”的参照，方向就错了。
- 结论：**面的形式统一靠“底色 + 半透明 + 同一套包边/阴影”**（`--sm-frame*`），不要在背景上加装饰层。
  连官方那层 `#7a9bf0` 混色也一并去掉了：`PANE_RULES` 的侧栏/对话区规则、`CHAT_BG`、composerSeat 的雾带
  现在都是纯 `color-mix(<底色> X%, transparent)`，皮肤里 `linear-gradient` 只剩“雾带本身”和色域图的
  饱和度条这两处功能性用法。
  背景装饰会跟用户自己选的颜色打架（远色相发脏），也很难解释“为什么这里多了一层”。
- `PANE_RULES` 里那串渐变保留 —— 那是复刻官方 `[data-platform=darwin]` 的规则，只在用户调过
  侧栏/对话区透明度时才注入，属于“回到官方观感”，不是新装饰。

### 半透明目标的观感永远依赖底层

**什么时候读**：用户说“我设了同样的颜色和透明度，为什么看起来不一样”。

- 透明度是折进值里的 `color-mix(<色> X%, transparent)`，**是叠在底下的层上，不是覆盖**。
  所以在两个不同底上给同一个 30% 蓝，出来的颜色一定不同，这不是 bug。
- 各目标真实的底：
  | 目标 | 叠在什么上面 |
  |---|---|
  | 当前对话底色 / 运行中 / 完成 / 工作区卡片(描边) | 侧栏列（`sidebar-fill`，macOS 还叠了 `#7a9bf0→#8f89b8` 渐变 + 原生 vibrancy 半透明） |
  | 气泡 / 卡片 / 代码块主体 / 工具输出块 / 行内代码 / 交付文件卡片 / 输入框 | 对话区 `bg-base` |
  | 嵌套卡片 | 「卡片」`bg-layer-1` |
  | 已编辑文件（头行 / 文件行） | 「卡片」`bg-layer-1` |
  | 菜单 / 弹层 | 页面，且自带 `backdrop-filter` 模糊，透出来的是模糊后的背景 |
- **侧栏是最特殊的一块**：它有官方渐变 + 40% 半透明 + 原生毛玻璃，底下本身偏蓝紫，
  同样的半透明色叠上去会比对话区里的更“蓝”。想让两处完全一致，只有两条路：
  1. 都用**不透明色**（滑条 100%）—— 实色不受底层影响；
  2. 接受差异，按各自底色调浓度补偿（气泡通常要比侧栏行低一档才看起来接近）。
- 排查口径：先确认两边底是否同一层（侧栏行 vs 对话区＝不同层），再看滑条值，最后才怀疑插件。
- **token 覆盖不要走 `theme.overrideTokens`，改成自己写带 `!important` 的样式表**：
  官方每次切会话都会重写 `body` 上的 token 快照（普通内联），经 ui-theme 下发的覆盖层会被顶掉；
  我一开始只在切会话时 `reapply` 补一遍，用户实测“还是丢”（触发点抓不准）。最终做法是
  `style[data-plugin-css="…-tokens"]`，内容为
  `body{--token:值 !important;…}` + `body[data-ds-dark-theme]{--token:值 !important;…}`。
  `!important` 声明压过普通内联，深浅两条规则跟主题走，切会话也不会被清。
  代价：别的插件想再覆盖同名 token 也得带 `!important`，否则会被我们压住。
- **切会话后“本来不透明的面突然透了、打开设置页又好了”＝覆盖层被重置**：官方在切会话时会重写
  `body` 上的 token 快照，`overrideTokens` 那层随之失效；而皮肤原来只在**设置页挂载**和 look 变化时
  才 `applyLook()`，所以现象是“切一次变透明，打开外观页立刻恢复”。
  修法：`watchChatLayers(onRebuild)` 在检测到主列重建时回调 `reapplyTheme()`
  （只重建 token 覆盖 + 自有变量，不碰标题/favicon/标语），和对话区透明度的自愈共用同一个节流点。
  同类症状可以类推：任何“要打开设置页才生效”的问题，先查是不是只在挂载/改值时 apply。
- **切换会话会改变“透出来的东西”，而不是改变你设的值**：空会话（hero）时 `composerSeat` 没有那层雾带、
  后面也没有消息，输入框/气泡底下是空的；进了会话就都有内容了，半透明的面立刻显得“更透”。
  用户的说法通常是“一切换对话就输入框透明了”——先让他把那一项的透明度拖到 100 验证，再决定是否
  改成默认不透明。同类的还有：输入框上渐隐、代码块语言条、已编辑文件卡片、交付文件卡片、气泡——
  这些元素本身**只在有内容时存在**，存在性随会话变，不是样式丢。

### 目标不止 token 一类

- 外观页的目标分三种 `kind`，合成一张表后统一读写，加新东西就是加一行：
  `token`（走 `overrideTokens`，背景类）、`paint`（直接写组件颜色，如图标 stroke、名称两段 color）、
  `group`（按 workspaceId 逐个上色）。
- `paint` 类默认不用 CSS 变量：`stroke: paint.iconColor ?? 'currentColor'`，设过就用、没设就继承主题，
  「恢复这一项」把 key 从 `look.paint` 删掉即回到继承。**但官方组件改不了属性**时（比如侧栏行悬停出来的
  省略号 / 置顶 / 归档图标），paint 要落成 CSS 变量 + 规则：`applyPaintVars()` 把
  `look.paint.rowIconColor` 写成 `html` 上的 `--ys-row-icon`，规则写
  `[data-row-key] [class*="rowActions"] svg,[data-row-key] [class*="iconButton"] svg{color:var(--ys-row-icon,currentColor)}`
  —— 变量缺省时 `var()` 回退 `currentColor`，等于官方原样；用 `color` 而不是 `fill`/`stroke`，
  因为官方图标两种写法都有。
- `paint` 类不用 CSS 变量：`stroke: paint.iconColor ?? 'currentColor'`，设过就用、没设就继承主题，
  「恢复这一项」把 key 从 `look.paint` 删掉即回到继承。
- **工作区色带已删除**：曾经按工作区逐组设色（`look.groups[workspaceId]`，染色用
  `row.style.box-shadow: inset 3px 0 0`），后来合并成一条统一配置，用户最后要求整块不要了。
  删除时的注意点：只删存储和 UI 不够，**必须留一个 `clearGroupTints()`** 把老版本写在行上的内联
  `box-shadow` 和 `data-ys-group` 标记清掉（选择器带上 `[data-ys-group]` 认领，别误删官方自己的阴影），
  否则升级后侧栏仍留着一条旧色带，看起来像“没生效”。`groups` 字段本身不再读入，下次 `writeLook` 自然消失。

- 图之外一定要留一个颜色值输入框（用户会要，别等第二次提）：受控 state 存原始文本，
  `editing` 变了就重置成 hex 回显；`onChange` 里只有 `parseColor` 通过才写 store，
  `onBlur` 回显归一化 hex。解析要同时吃 `#rrggbb`、裸 6 位、大写和 `oklch(L C H)`；
  底层照存用户输入的原始字符串（oklch 精度比 hex 高），只有显示层统一成 hex。

### 色阶派生（一个主色 → 十档）

- 官方色阶在 OKLCH 里是等色相 + 固定亮度阶梯：263° 附近，50 档 `L=0.963` 到 900 档 `L=0.313`，
  彩度比相对 500 档为 `0.09 / 0.13 / 0.24 / 0.44 / 0.75 / 1.04 / 1.00 / 0.68 / 0.27 / 0.19`。
- 派生只要两件事：色相和彩度换成主色的，**亮度阶梯保持不变**；主色与 500 档的亮度差按档位加权
  跟随（两端给 0.1~0.5 的权重），否则浅档会冲成纯白、深档压成黑。
- 实测：seed `#4176e6` 还原出官方的 7 档，seed `#d9661a` 得到 `#fdf2ec → #443229` 的完整橙阶，
  500 档精确等于选中的主色。
- 输出用 `oklch()` 字符串即可，让浏览器做色域映射；自己转 hex 要手写 gamut clamp，没必要。
- 主色不要只收 hex：色域图里直接存 `oklch(L C H)`，比「hex 转换 → 回读」少一层精度损失；
  解析侧同时接受 `#rrggbb` 和 `oklch(…)`。favicon 和 hex 回显才需要 hex，
  写一个 `oklchToHex` 把通道夹到 [0,1] 即可。
- **色域图的横轴是色相，所以“最低亮度”在不同横向位置是不同颜色的暗版**（红→棕、绿→深绿），
  这是 OKLCH 平面的本质，不是偏色（贴边裁剪造成的偏色是另一回事，见 `maxChroma` 的 0.96 余量）。
  要选黑白灰：浓度带拖到最左（彩度 0）能让整张图退化成灰阶；另外单独加了一条灰阶条
  （`.ys-pal-gray`，白→黑，`pickGray` 取 `oklch(1-x, 0, H)`），横向点哪都是无彩色，
  且不影响已有的色相/浓度设置。
- 选色入口做成「一张能拖着走的全颜色图」，别做色板格子，也别做 H/C/L 数字滑条：
  用户原话是「我直接移动去选，不要参数，就是一个全颜色的图」。canvas 逐像素画 OKLCH 色域即可——
  横轴色相、纵轴亮度、彩度取该点 gamut 边界（`maxChroma` 二分 14 次，判据是三个线性通道都在 0–1），
  再乘一条「灰 → 最艳」浓度带的比例；`pointerdown` + `setPointerCapture` + `pointermove` 连续选。
  一张图里红橙黄绿蓝紫和深浅同时都在，不用解释。
- **不要用 CSS 渐变模拟色域图**：CSS 表达不了「每一行彩度上限不同」，会压平成几块死色。
  要真实形状只能逐像素算。
- 逐像素算 gamut 边界很贵：320×180 每像素二分约 92 ms，拖浓度带会掉帧。
  按 2×2 块取一次边界再填块内像素，降到约 18 ms，肉眼无差。
- 主色等于官方蓝时**不留覆盖层**，默认态像素级等于官方；否则一进来就有浮点级偏色。

### 侧栏面板入口与「更多」菜单

**什么时候用**：要加/去掉侧栏面板图标，或往「更多」菜单里加行、把官方入口折进去。

- 面板图标来自 `sidebar.panellist` 槽位，各自官方包注册：插件 = `dsh-client-ui-plugin-manager`（order 0），
  自动化任务 = `dsh-client-ui-schedule`（order 10，主面板 id `schedules`）。
- 「更多」菜单行来自 `sidebar.panellist.actions`；官方那两行（浏览更多插件 / 创建你的插件）由
  `dsh-client-ui-entry-customization` 注册。**想去掉这两行，用 `plugin_manager` 的 `set_plugin`
  禁用 `include:entry-customization`**（profile 配置，升级不覆盖，比 DOM 补丁稳），代价是它的全部能力一起关掉。
- **没有注销别人槽位注册的 API**：`slots` 只有 `register` / `registerFactory` / `inject`。
  要把官方面板入口折进「更多」，只能：运行时隐藏原图标（`button[aria-label]` 匹配 + `MutationObserver`
  + 订阅 `ctx.locale` 跟随语言切换）+ 自己注册一行 `sidebar.panellist.actions`，点击走
  `ctx.layout.selectPanel('<panelId>')`。属兼容补丁，官方改 label/结构就失效。
- 「更多」按钮只在 `sidebar.panellist.actions` 有注册项时出现；把行全删光等于把按钮也删了。
- **实测（已回退）**：把「自动化任务」折进「更多」+ 隐藏原图标后，用户反馈任务页宽度不对、要求放回官方位置——`more-menu` 包已删，图标恢复。教训：面板入口挪位会改变用户对页面的预期，没有明确收益别动官方入口。禁用 `entry-customization` 后若不注册行，侧栏「更多」会整个消失，属预期。

### 坑

- macOS 上侧栏不是纯色：`[data-platform=darwin]` 叠了一层 `linear-gradient` +
  `color-mix(fill 97%, #7a9bf0)` + 40% 透明度。改 token 生效，但观感是「淡蓝渐变 + 半透明」，
  要完全控制得覆盖 `.sidebarCol` —— 类名是构建期 hash，升级会变。
- 深浅必须成对给：`preference: system` 的用户会随时切主题，只给 light 会在深色下穿帮。
- 静态色阶定义在 `:root`、alias 在 `body`：覆盖要落在 `body` 上，写到 `:root` 只换色阶，
  单独覆盖了某个 alias 就压不住。
- 官方色阶名（`--dsw-static-deepseek-*`）和两个背景 token 是稳定契约，install 时自检探一条
  `getComputedStyle(document.body).getPropertyValue('--dsw-alias-bg-base')` 非空即可。
- **改了背景色像没反应，先看那个 token 的基准值是不是白色**：对话区 `--dsw-alias-bg-base`
  在浅色下就是纯白，换成浅灰差异小到看不出来，用户会以为"只有文件区能改"。
  侧栏反而明显，因为它还有一层 40% 透明度和一条渐变。
  验证办法是调透明度滑条（半透明后立刻能看到露出的 vibrancy），或者直接读
  `getComputedStyle(document.body).getPropertyValue('--dsw-alias-bg-base')` 确认写进去了。
- **canvas 图全白 + 拖不动，先查 ref 有没有真的挂上去**：元素 ref 为空时，
  `useEffect` 里 `if (ref.current === null) return;` 会静默跳过绘制，`pointerdown` 里的
  `getBoundingClientRect` 也直接 return —— 两个症状一起出现，而且不报错、不看控制台发现不了。
  写完 JSX 回头用 grep 确认 `ref: xxxRef` 在元素上出现过，比看现象快。

## 官方升级后的失效面与自查

**什么时候用**：DSH 升级之后（尤其发现某个装饰“突然没了”），或者要给新插件评估脆弱点。

### 抗升级的三条原则

1. **优先属性，其次 local 名，最后才是构建 hash**：
   `data-*` / `aria-*` > `[class*="_output_"]` 这类 local 名 > `_block_8z71b_1` 这种带 hash 的类名。
   带 hash 的规则在下次官方构建后必失效 —— 命令块就是这么踩到的。
2. **拿不到稳定属性时，用 `:has()` 从内层反查外层**：命令块的根没有 data 属性，但根里一定有
   `_command_`，所以写 `[class*="_block_"]:has([class*="_command_"])` 就能定位到整块，
   不用知道 hash，也不会误伤代码块（代码块的 `_block_` 里没有 `_command_`）。
3. **关键锚点全部进自检**：皮肤现在探 18 条（标题/favicon/body token/输入区/气泡/思考/工具行/
   命令块/代码块/语言条/已编辑文件/交付文件/行内代码/侧栏列/侧栏行）。内容类锚点用 `whenChat()`
   包一层——没有 `[data-chat-turn]`（空白会话）时视为通过，否则每次启动都会误报。

### 一次升级必查的锚点（0.2.1-rc.3 实测仍成立）

- 侧栏行：`data-row-key="session:<id>"` / `"workspace:<id>"`、`aria-selected`、`aria-expanded`、
  `div.groupSection` 上的内联 `--dsh-workspace-indent`。
- 布局类名（CSS modules local 名，hash 会变、local 名稳定）：`[class*="sidebarCol"]`、`[class*="centerCol"]`、
  `[class*="composerSeat"]`、`[data-composer-dock]`、`[data-phase=active]`。
- 槽位：`conversation.composer.dock`、`conversation.input.dock`、`conversation.input.left|right`、
  `conversation.chat.node`、`conversation.hero.brand.mark`、`sidebar.brand.mark|name`、
  `sidebar.panellist.actions`、`sidebar.workspaces.session.menu.item`、`sidebar.workspaces.session.row.action`、
  `sidebar.session.row.leading`、`settings.plugins.tab`。
- 投影：`tokenUsage` / `contextPressure` / `modelSelection` 都在；**`usageByRoute` 已不存在**，
  usage-cost 会退到 legacy `tokenUsage`（不崩，但分路由/峰谷拆分会缺行）。
- 宿主事件：`approval/request` 仍在。DOM 锚点：`[contenteditable]`、`[data-chat-turn]`、
  `[class*="_userRow"]`、`head > title`、`link[rel=icon]`、`body` 上的 `--dsw-alias-*`。

### 三个反复会踩的坑

- **状态点只有 ongoing 是 `svg`**：`StateDot` 的写法是 `state === "ongoing" ? <svg data-state="ongoing"> :
  <span data-state={state}>`。所以选“完成”千万别写 `svg[data-state=done]`（永远不命中），
  要么 `:has([data-state=done])`，要么按 state 值判断。写选择器前先确认标签是 svg 还是 span。
- **内容类锚点必须标 optional，否则自检会天天误报**：气泡、思考块、工具行、命令块、
  代码块、语言条、已编辑文件、交付文件、行内代码 —— 这些东西**启动那一瞬间屏幕上没有**
  （历史还在渲染、会话虚拟滚动只渲染可视区、这个会话根本没用过 present）。把它们当硬锚点，
  每次启动都报“有变化”，自检就废了，真出问题时也没人信。
  做法：探针带 `optional: true`（skin 用 `whenChat()` 统一加），miss 时归到 `unchecked`
  而不是 `misses`；自检页把 unchecked 显示成「这次界面上没有出现，未检查（不算失效）」。
  只有 `head > title`、favicon、body token、`contenteditable`、`[data-composer-dock]`、
  `composerSeat`、`sidebarCol`、`data-row-key` 这些**启动就该存在**的才硬判。
- **ScrollRestore 会克隆离场的行**：新版侧栏为退出动画 `cloneNode(true)` 再 `removeAttribute('data-row-key')`
  并设 `inert`。我们在行里插的徽标（转圈/数字）会跟着被复制，克隆体里再转一次。
  一条 `[inert] .sm-run{display:none}` 收掉；选择器本身因为克隆没有 `data-row-key` 不会命中。

### 自查顺序

1. 先看 `~/.dsh/storages/self-check/*.json`（宿主半）和设置 → 插件 →「自检」页（客户端半），
   有 `misses` 就直接是“哪条锚点 → 哪个功能没了”。
2. 再按上面「必查锚点」逐条在 asar 里搜一遍（`strings`/python 读 `Contents/Resources/app.asar`
   头 4 个 uint32 拿 JSON 头，再按 offset 切片），比在界面里点半天快。
3. 修的时候优先换**稳定的等价物**：属性/槽位 > 类名 hash；`:has([data-state=…])` > 依赖标签名；
   能靠 CSS `order`/变量解决的别改 DOM。

## 配置基准、恢复与升级体检

**什么时候读**：升级 DSH 之后、怀疑插件“神秘消失”、界面白屏、换机重建 profile。

### 为什么配置文件要进仓库

插件加载失败**不报错、不弹窗、界面里仍然显示「已启用」**。`loadProfileDirectory` 对每个
bundle 单独 try/catch，失败只塞进 `skippedBundles`，由 `reportSkippedBundles` 写 Host 的
stderr；桌面端只在崩溃时才把它打进 crash report。所以“插件没加载”这件事必须靠外部体检发现。

现在的做法：`profile/` 存一份配置基准（可推送），配三个脚本。基准里 `link:` 路径脱敏成
`{{REPO}}`，恢复时再渲染回本机路径 —— 仓库公开也不泄露本机目录。

### 四条“集体消失”路径

1. **包解析不到**（`link:` 指向的目录没了/卷没挂）：该 bundle 被跳过，其余照常启动，rc=0。
2. **前端组合失败**：任一包 `exports["./client"]` 缺文件或 `dsh.client` 声明非法 →
   `ClientModuleRegistry` 构造抛 `ClientPackageCompositionError`，`__DSH_BOOT__` 整批不下发，
   **整个界面起不来**（不是单个插件没了）。
3. **致命启动失败后的「禁用第三方插件」**：`sanitizeProfile` 把 `cordis.patch.yml` 改名成
   `.bak-<ts>`、`bundles` 重置成 base+web-app，`dependencies` 保留 —— 能救，但要先知道备份在哪。
4. **兼容性门**：`engines.dsh` 或 `@deepseek-ai/dsh*` 的 peer 不满足运行版本 → 跳过，
   要 `compatibility.json` 精确豁免（`名@版本` → `[dsh版本]`）。**别给插件加 `engines.dsh`**，
   现在全部没写，升级不受影响。

### 四个脚本

- `scripts/doctor.sh` — 配置漂移 + 插件真加载没。内部把 profile 复制成临时 `diag`、在临时
  `DSH_HOME` 里 `--dump-config`，只读真实 profile。
- `scripts/profile-sync.sh` — 现状 → 基准（`--check` 只比较）。
- `scripts/profile-restore.sh` — 基准 → 现状，默认只补不删；`--force` 才完全覆盖。
- `scripts/check-clients.sh` — 提交前闸门：exports 指向的文件在不在、`dsh.bundle`/`dsh.client`
  字段形状、`node --check` 语法。防的是上面第 2 条。
- doctor 还会扫 `cordis.patch.yml` 里 `insert` 引用的包（如 `dsh-purge`）：它们不在 `bundles`
  列表里，换机重建时恢复脚本写了 patch、包却要另装，这一项就是抓这个缺口。

### 启动对账（self-check 插件里的那一条提示）

`~/.dsh` 之外没有任何东西会在升级后提醒你，所以提示做进了 `self-check` 的客户端半：

- 宿主把 `__DSH_BOOT__ = { rev, release: { version, commit }, entries, batches }` 注入页面；
  `entries[].id` **就是包名**（`graphRow(packageName, …)`），被跳过的 bundle 不在这里出现。
- 启动 rAF 后比对三件事：版本号、`@local/*` 实际出现的包、`EXPECTED` 硬编码名单。
  版本变了 → 弹「DSH 已升级 X→Y」；名单少了 → 弹「这些插件没加载」。
- **没确认就再弹**：`dsh.self-check.watch` 存基线 `{version, plugins, missing}`。发现问题时
  **不推进基线** —— 直接关窗口（没点「知道了」）下次启动还会弹，点了才把基线推到当前状态。
  首次安装没有基线时只记录不弹，避免刚装就骚扰。
- 提示是自己画的 fixed 卡片（`.sm-alert`），**不用官方 Toast**：Toast 要挂进 slots 的
  overlay 才拿得到完整上下文，一条启动提示不值得为此增加对 `ui-primitives` 的依赖。
- 自检页里只显示状态：当前版本 / 上次启动版本 / 已加载 N 个 / 缺谁。不做「预览」按钮 ——
  提示本身已经由启动逻辑触发，不需要一个只为演示存在的手动入口。
- 回归测试 `self-check/test/watch.test.mjs`：用 node 模拟 `window/document/localStorage`，
  跑 `inspect()` 和点击链路，覆盖“首次不弹 / 升级弹 / 缺包弹 / 未确认再弹 / 确认后不弹 /
  拿不到版本不炸”。改提示逻辑先跑它。

### 坑

- **`EXPECTED` 名单要跟着插件增删走**：加一个 @local 插件忘了写进去 → 少一个不报（只是漏报）；
  删了插件忘了删 → 每次启动都弹「X 没加载」的误报。
- **desktop 被 Electron 独占**：`dsh plugin --profile desktop ...` 直接报
  `profile "desktop" is managed exclusively by the Electron application`。所以恢复只能是文件操作，
  `profile-restore.sh` 是唯一允许手改 profile 清单的地方（改完跑 doctor 复查）。
- **asar 里的路径 bash 的 `-f` 看不见**：判断 DSH 在不在要测
  `Contents/Resources/app.asar` 存在 + `MacOS/DSH` 可执行，别去 `-f` asar 内部的 `bin.js`。
- **复制 profile 必须改名**：临时 profile 叫 `desktop` 会撞独占；叫 `diag` 之类，配合
  `DSH_HOME=<临时目录>`。
- **`{{REPO}}` 里有空格**：仓库路径带空格，所有脚本里都加引号，python 侧用 `os.path.realpath` 比对。
- **restore 默认 merge**：只补不删，所以恢复后 doctor 可能报“多了加载项 X（基准里没有）”——
  那是你后来装的、还没 sync 的东西，跑一次 `profile-sync.sh` 就对齐，不是故障。
- **别把 `profile/` 当插件包**：它只有配置，没有 `index.js`，误跑 `install_bundle` 会失败。

### 回退

`profile-restore.sh` 每次写清单前留 `package.json.bak-<时间戳>`；patch 被官方改名后由脚本把
最近的 `.bak-*` 改回来。想彻底回到官方初始态用 `--from-default-profile web`，但那会清掉
用户层 patch —— 先备份 `profile/` 里的基准。

## 侧栏行锚点：标注与运行中样式

**什么时候用**：给侧栏会话/工作区行加标记、状态样式。

### 行的 DOM 锚点

- 行元素带稳定属性 `data-row-key="session:<id>"` / `data-row-key="workspace:<workspaceId>"`
  （未分组桶是 `workspace:` + 空 id）。官方 className 是构建期 hash，别拿它写选择器。
- 当前打开的会话行是 `aria-selected="true"`，纯 CSS 就能做强高亮，不用跟踪 sessionId。
- 标题 span 没有稳定属性，要自己在装饰 pass 里打标记（如 `data-sm-title`）再写 CSS：
  会话行取 `row.children[1]`；工作区行取 `row.children[row.children.length - 2].firstElementChild`
  （倒数第二个是名称格，最后是悬停按钮格；行里插了别的元素这个定位也成立）。
- 工作区行的子格顺序是 `[文件夹格, 箭头格, 名称格, 行动作格]`（hover 时文件夹格换箭头格）；
  在 `children[2]` 之前插转圈/数字徽标，得到「文件夹图标 → 转圈 → 数字 → 名称」。
- 每个工作区组是一个 `div.groupSection`，内联样式带 `--dsh-workspace-indent`（逐层
  `style.getPropertyValue` 就能找到，hash className 别用）；展开的会话行、「显示更多」按钮
  （`data-row-key="overflow:…"`）和嵌套子组都挂在里面。官方行自带圆角、行间有 2px 间隔。
- 装饰用 `MutationObserver` 监听行增删 + `aria-expanded` 属性变化 + `sessions.list` / `workspaces.list`
  订阅，rAF 合批；必须在 `attributeFilter` 里只留 `aria-expanded`，别监听全量属性变化，
  聊天流式更新会把回调打满。行的 running 判断用
  `sessions.list.getSnapshot().byId[id].running`；工作区“有会话在跑”用
  `workspaces.list.getSnapshot().items[].sessionIds` 求交集（折叠的组看不到子行，不能从 DOM 推）。

### 样式层级

- **输入框光标不是文字色，是品牌色**：官方 `.input{caret-color:var(--dsw-alias-state-business-primary)}`。
  所以把主色调成白色/极浅色时，光标会和输入框背景同色 → “光标不见了”。
  皮肤里已固定成 `html [class*="composerSeat"] [contenteditable="true"]{caret-color:var(--dsw-alias-label-primary)}`。
- **运行行也不要改标题颜色**：曾经 `[data-sm-running] [data-sm-title]{color:business-primary}`，
  主色一旦是白色，运行中的标题就变白、在选中底色上看不清。运行行只保留字重 600 + 底色，
  文字色交给主题的 `label-primary`。
- **一批“20% 透明白”的统一做法**：皮肤里抽了 `GLASS20 = color-mix(in srgb,#fff 20%,transparent)`，
  思考块 `[class*="thinkBody"]`、已编辑文件（头/行）、代码块语言条、代码块主体都用它当默认
  （`var(--ys-*, ${GLASS20})`，用户设过就以变量为准）。深色主题下是提亮、浅色主题下几乎不可见，
  这是 20% 白在两种主题下的必然差异。
- **代码块主体改成 paint 面**：shiki 在 `pre` 上写的是**内联** `background-color`，样式表压不过，
  必须 `!important`；所以它不再走 token（`--shiki-background`），改为 `--ys-code-block` + 提权规则。
- **选中行只改底色，别动文字**：曾经给 `[aria-selected=true]` 的标题加 `color:label-primary;font-weight:700`，
  用户明确不要（“字体颜色不要变，包括转圈和文件数”）。转圈和运行数字本来就是 `business-primary`、
  不随选中变化，所以整行唯一的区别就是那层 85% 透明白底色。
- 层级：当前会话行 ＞ 标注 ＞ 运行中提示。同一份样式表按“运行中 → 标注 → 当前”排规则，后面的赢。
- **运行中的行也有底色，比选中行淡得多**：运行中的会话行 + 运行中的工作区行（含未分组桶）都染
  同一层，`--sm-run-fill` = `rgba(255,255,255,.45)`，选中行 `--sm-open-fill` 是 `rgba(255,255,255,.85)`
  （定稿前两者都是商业蓝 30%，用户改成**透明白**：运行行 45%、选中 85%）。
  不跟主色走的好处：主色改成白色或深色都不串色，浅色/深色主题下是同一层提亮。
  **这两个自定义属性声明在 `body{…}`，不在 `:root`**
  （原因见「token 的权威位置」：`:root` 里引用 alias 会让整条值失效，选中底色一起没掉），
  使用处还要写内联兜底 `var(--sm-run-fill,rgba(255,255,255,.3))`。运行行写在
  `[data-row-key][data-row-key][data-sm-running]:not([aria-selected=true])` 上：重复属性抬 specificity
  盖过官方 `:hover` 灰底（否则鼠标一划过蓝底就没了），`:not` 把选中行让给更重的选中规则。
- **跑完还没看（完成未读）的行用同一个 40%**：官方状态点由 `sessionStatuses` 决定，
  `node.completed`（= `completionUnread === true`，进过该会话就清掉）渲染成 `svg[data-state=done]`，
  所以纯 CSS 用 `[data-row-key^=session]:has(svg[data-state=done])` 就能命中，不用在装饰 pass 里记状态；
  同样带 `:not([aria-selected=true])` 让选中行赢。别从 `completionUnread` 走数据层：多一条订阅、
  还要处理刷新时机，`:has` 跟着 DOM 自己变。
  **别让运行行跟选中行同浓度**——用户要的是“像选中、但淡很多”；45% 对 85% 就是这条界线。
- 标注 = 名称底部 2px 黑色下划线（`text-decoration` 打在 `[data-sm-title]` 上，会话/工作区同一规则），
  **不做整行底色、不改标题颜色**（用户明确不要整行高亮）。标注是纯开关：菜单点一下标记、再点取消，
  **无弹窗、不选色**；色键只是存储占位（客户端固定写 `red`），宿主只认 `marks.js` 里 `COLORS` 的 6 个键。
- 当前会话行只留浅色底（`--sm-open-fill`），**不加左侧竖条**：以前用 `inset 2px box-shadow` 竖条，用户要去掉。
  想盖过官方 `:hover` 底色，用 `[data-row-key][data-row-key][aria-selected=true]` 重复属性抬 specificity，别用 `!important`。
- 转圈是 `StateDot`（`svg[data-state="ongoing"]`，内部 `g` 做 1.5s 旋转，`stroke: currentColor`，
  颜色是 `--dsw-alias-label-tertiary`）。放大改色纯 CSS（`transform: scale(1.25)` + `color`）就行；
  工作区行自己画同款 `<circle>` 轨道 + 弧线插进 `children[2]`（文件夹/箭头格之后、名称之前），
  外面包一层 `.sm-run`（转圈 + `.sm-run-count` 数字徽标，数量 = `sessionIds` ∩ 运行中集合），
  记得 `prefers-reduced-motion` 兜底。
- **工作区行只留一个转圈**，顺序固定「文件夹图标 → 转圈 → 数字 → 名称」：热更新后旧 `.sm-spin`
  徽标会残留在行里（双转圈），装饰 pass 里清掉；行内其他 `svg[data-state="ongoing"]`（官方自带的）
  一律 `display:none`，注意用 `closest('.sm-run')` 排除自己的、`closest('[data-row-key]')` 排除子行的。

### 工作区组框

**什么时候用**：给工作区组加视觉包裹，让工作区和普通对话区分开。

- **只有展开的工作区才有框**：展开时包住工作区行 + 其下所有会话行，折叠时不画框
  （用户明确要求折叠态干净）；四边是直的，只有整体四个角圆角。
- 展开状态取工作区行的 `aria-expanded`（官方 `ProjectRowItem` 直接写 `row.expanded`）；属性缺失时
  退化为「组容器里有会话行」。官方折叠时 `deriveGroups` 把 `sessions` 置空，容器里本来就没有会话行，
  两条判据一致。空组展开没有行增删，所以还要监听 `aria-expanded` 属性变化。
- 做法：**框画在官方分组容器 `div.groupSection` 上**（`data-sm-frame="group"`，border + 圆角 + 少量
  padding），一个容器一个框，天然就是完整方框，行的圆角和间距都不用动；嵌套子组各自成框。
  没有容器的行在按行拼框前要先判展开，折叠的单行组一个字都不打。
- **卡片感**（苹果原生质感，阴影宁轻勿重）：组容器带淡底色和轻阴影——`--sm-frame` 发丝描边
  （`color-mix(in srgb, var(--dsw-alias-label-primary) 22%, transparent)`，跟着主题反色：浅色下淡灰线、
  深色下淡白线；**别用纯白 1px，显脏显粗糙**）；`--sm-frame-fill` 底色 `label-primary 5%`；
  `--sm-frame-shadow` 只留一层零偏移、零扩散的匀影（`0 0 14px rgba(0,0,0,.10)`，四边四角完全一致，
  浓度微调只动这个透明度；0.08 时用户嫌淡、0.10 认可）；浓淡经验：0.2/0.4 量级“阴影太重”，
  多层叠加糊在直边上会“四边发黑”，定向下坠影会让四边不匀——**用户要的是四边跟顶边一样匀**，
  别再加接触影和下坠影）；
  `--sm-frame-lift` 1px 白色 inset 高光（深色主题下才明显）。
  **坑：负 spread 会吃掉圆角**——阴影圆角 = `border-radius + spread`，`-8px` 负扩散把 12px 圆角的
  影子压成 4px，四个圆角处影子向内塌陷，看起来“角直接没了”；晕影想淡就调低透明度，别用负扩散。
  **阴影只往下落，卡片顶边全靠描边 + 均匀晕影**：描边不够（12%/16%）或卡片间距不够时，上一张的投影
  会落进缝隙糊住下一张的顶边，表现为“底部没问题、顶部看不清”——描边给到 22%、
  `margin-bottom: 18px` 让投影落在空处；顶边的影来自零偏移的均匀晕影层。
  圆角 12px、`padding: 3px`、`margin-bottom: 18px` 给阴影和顶边留出干净的空处，
  不靠官方 `.groupSection+.groupSection` 的 4px（那条规则 specificity 更高，覆盖不掉）。
- **坑：滚动容器会裁剪卡片阴影**。侧栏列表是 `overflow-y: auto`（左右方向同样裁剪），
  顶部没有 padding，第一张卡片的晕影整圈被裁掉、看起来“阴影不显示”。做法：装饰 pass 里从组容器
  往上找第一个 `overflowY` 为 auto/scroll 的祖先，打上 `data-sm-list`，CSS 给它
  `padding-top: 8px` 留出影子落点（selector 用 `[data-sm-list][data-sm-list]` 抬 specificity 压过官方 padding）。
- 底色是半透明叠加，所以会话行 hover（官方 `--dsw-alias-interactive-bg-hover`）和当前行高亮
  仍然盖在卡片上、不会打架；**按行拼框的退化路径不加底色和阴影**，只有边框，否则每行一条阴影很脏。
- 三档可调：`--sm-frame` 框线颜色（发丝描边，跟着主题反色）、`--sm-frame-fill` 底色、
  `--sm-frame-shadow` 阴影。
- 没有分组容器的行（扁平列表等）退化为按行拼框：按 DOM 顺序把「workspace 行 + 其后连续
  session/overflow 行」划成组，给组内每行打 `data-sm-frame=first/mid/last/only`，用行自身的
  `border` 拼框（`box-sizing: border-box`，不改行高）。容器要**先登记再判是否画框**（`claimed`），
  否则折叠组的单行会掉进拼框分支又长出一个框。
- **坑：行自带圆角会把拼接的边线掰弯**，每条对话旁出现一段段弧。按行拼框时必须强制
  `border-radius: 0`、`margin` 清零让行贴合，圆角只留给首行上两角、末行下两角；
  `last/only` 加 `margin-bottom` 分隔相邻组。
- **坑：会话行可能嵌在工作区行内部**（两种 DOM 都见过）。用
  `rest.every(row => first.contains(row))` 判定嵌套，嵌套时只给最外层行打 `only`，别再给子行拼边。

### 工作区「…」菜单没有槽位

- 会话行菜单是槽位（`sidebar.workspaces.session.menu.item`），工作区行的「重命名/删除」菜单
  **写死在 ProjectRowItem 里**，只能 DOM 注入克隆官方菜单行（`div.itemWrap > button[role="menuitem"]`，
  克隆第一个 itemWrap 换图标和文字）。
- **坑：`role="menu"` 的直接子元素不是菜单行**。官方 Menu 把行包在内部的 viewport div
  （`role="presentation"`）里，找行必须 `menu.querySelectorAll('button[role="menuitem"]')`
  取每个按钮的 parentElement；拿 `menu.children` 数行永远数不到，`rows.length < 2` 这类门槛
  会让注入静默失效（工作区标注曾经整块丢过）。注入位置是最后一个 itemWrap 之前。
- 注入前要确认这个菜单是工作区行开的：pointerdown 捕获阶段记下 `closest('[data-row-key^="workspace:"]')`
  的行和当时的 `className`，菜单出现时行的 className 变了（menuOpen 类）才注入。
  **注意 `aria-expanded` 是行的展开状态（文件夹），不是菜单状态**，不能拿来判断。
- 点完注入的行要自己关菜单：向 `document.body` 派发一个冒泡的 `pointerdown`，
  官方 Menu 的“点外面关闭”会把它当点击外部。
- 注入行的排布要和会话菜单对齐：标记贴着删除（会话里标记=470）；图标也用同一套字形，
  用户才觉得“一模一样”。
- 官方 DOM 一改就失效，属于兼容补丁，升级后要复核。

### 标注存储

- 标注放 `<DSH_HOME>/storages/sidebar-marks/marks.json`（原子写 0600，坏文件隔离成
  `.corrupt-*`，同 session-delete 的队列文件）；只存 id + 颜色键 + 时间戳，不存标题和路径。
  标注是开关式：已标记再点一次写 `color: null` 删条目；色键只是占位，显示恒为黑色下划线。
- 路由走 `ctx.connection.fetch.register`：GET state / POST mark；页面用相对路径 `api/...` 调。
  多标签页用 `BroadcastChannel` 互通。
- 曾被删掉的功能：工作区置顶（`workspaceRegistry.insertBefore` 重排 + 图钉标记）已整体删除，
  别再凭印象加回来；`marks.json` 里的 `pinnedWorkspaces` 字段只在该版本之前存在，现在会被忽略。

### 升级自检（每个插件都有）

**什么时候用**：官方升级后功能静默消失，或新增插件要接入同一套自检。

- 每个客户端半都带一个 `selfCheck(label, checks)`：首屏后 `requestAnimationFrame` 跑一次，
  逐个 `probe()`；**只有所有探针都没命中时**才补一次 1.5s 重试（外壳还没挂载不算坏锚点），
  之后不再有任何定时器、观察器、轮询——检查完就零开销。
- 探针只查“启动时就该存在”的锚点（侧栏行 `data-row-key`、分组容器 `--dsh-workspace-indent`、
  输入框 `contenteditable`、`head > title`、`link[rel=icon]`、会话行），不查随内容出现的东西
  （如用户消息行）；这类用“不存在就视为未就绪”的宽容判定，避免空白会话误报。
- 报告格式统一：`[插件名] 自检：N 处官方锚点变了，受影响的功能：` + 每条 `· 锚点 → 影响` +
  指回本文档「升级后失效排查」。结果同时写进 `localStorage['dsh.self-check']`（每个插件一条
  `{ ok, misses, at }`），DevTools 或以后的面板都能读；宿主半只在宿主进程控制台输出。
- 宿主半（`workspace-ledger` / `approval-alert`）用 `ctx.get(service)` 探依赖的服务，
  缺了就 warn；`inject` 里声明的服务缺失本来会让插件在设置里显示 failed，自检只是补一条原因。
  结果同时写 `<DSH_HOME>/storages/self-check/<插件名>.json`（`{ ok, misses, at }`，0600）。
- **界面入口**：`self-check` 插件注册 `settings.plugins.tab`（order 20），页面读
  `localStorage['dsh.self-check']` 汇总，正常/有变化 + 每条 `锚点 → 影响`；宿主半的 JSON 路径写在页脚。
  页面只在打开时读一次 + 手动「刷新」按钮，不轮询。
- **纯客户端 bundle 也必须带宿主入口**：`exports` 的 `"."` 指向 `index.js`（可以是空 `apply()`），
  否则宿主 import 到 `client.js` 会报 `window is not defined`，安装显示 `application: failed`。
- **宿主半改动要 `remove_bundle` + `install_bundle` 才生效；客户端半刷新即可。**

### 坑

- 客户端样式表注入**别用“已存在就跳过”的 early return**：热更新后旧 `<style>` 标签会一直活着，
  之后所有 CSS 改动静默不生效（表现为“改了没变化”）。每次激活先清掉旧标签再挂新的。
- `ctx.get('workspaces')` 拿工作区控制器（`list.getSnapshot()`）算“有会话在跑”的数量，服务名
  没有就退化成不做工作区装饰，别让它挡激活。
- 官方菜单注入的行不在 React 的 items 里，`onSelect` 不会认，点击处理器要自己挂、`stopPropagation`。
- 菜单行用原生 `MenuItemButton`，克隆官方行只为了工作区菜单那个没有槽位的场景；
  `shell.overlay` 只挂失败 Toast。
